# طراحی `versline organize`: سازمان‌دهی آرشیو بزرگ فایل‌ها

[فهرست](index.md) · [راهنمای استفاده](organize.md) · [English guide](../en/organize.md) · **فارسی**

این سند طراحی کامل قابلیت `organize` است: هدف، اصول، مراحل، قالب فایل‌ها، الگوریتم‌ها و نقشهٔ راه. طوری نوشته شده که هر توسعه‌دهنده یا دستیار هوش مصنوعی دیگری (Claude Code، Copilot، Cursor و …) بتواند بدون دسترسی به گفت‌وگوی اولیه کار را ادامه دهد.

---

## ۱. مسئله

یک هارد چندصد گیگابایتی که طی سال‌ها از چند منبع پر شده است: لپ‌تاپ‌های قدیمی، فلش‌ها، پوشه‌های «دانلود تا تاریخ …» و یک کتابخانهٔ الکترونیکی نیمه‌مرتب. ویژگی‌ها:

- ده‌ها هزار فایل از نوع PDF، Word، صوت، ویدیو، تصویر (اغلب کتاب‌های اسکن‌شده: یک پوشه پر از jpg/tif)، نرم‌افزار و فایل فشرده؛
- تکرار زیاد (یک پوشه چند بار در جاهای مختلف کپی شده)؛
- نام‌های فارسی و عربی (با «ي/ك» عربی و «ی/ک» فارسی مخلوط)؛
- هارد هم روی **ویندوز** و هم روی **لینوکس** استفاده می‌شود؛
- کاربر نمی‌خواهد چیزی پاک یا جابه‌جا شود؛ ساختار مرتب باید **کنار** داده‌های فعلی ساخته شود.

هدف `versline organize`: ابزاری که این کار را مرحله‌به‌مرحله، قابل‌ادامه، قابل‌بازبینی و با کمترین هزینهٔ هوش مصنوعی انجام دهد و برای افراد دیگر هم قابل‌استفاده باشد.

## ۲. اصول (غیرقابل‌مذاکره)

1. **هیچ‌چیز پاک یا بازنویسی نمی‌شود.** همهٔ مراحل جز `apply` فقط‌خواندنی‌اند. `apply` فایل‌ها را **کپی** می‌کند (منبع دست‌نخورده) و فقط انواعی را که در `@media_kinds` آمده‌اند (پیش‌فرض صوت و ویدیو) **جابه‌جا (move)** می‌کند. جابه‌جایی فقط روی همان درایو و به‌صورت تغییر نام انجام می‌شود، پیش از انجام در دفتر ثبت می‌شود و با `revert-moves` کاملاً برمی‌گردد. (تصمیم کاربر، ۱۴۰۵/۰۸/۱۸: کپی ۳۰۰ گیگ صوت و ویدیو وقت و جای زیادی می‌گیرد؛ hard link هم کنار گذاشته شد.)
2. **هر مرحله قابل‌ادامه و تکرارپذیر است.** قطع برق یا بستن ترمینال نباید کار را خراب کند؛ اجرای دوباره از همان‌جا ادامه می‌دهد و کار انجام‌شده را تکرار نمی‌کند.
3. **هیچ کپی‌ای بدون برنامهٔ تأییدشده انجام نمی‌شود.** تصمیم‌ها (دسته‌بندی، مقصد، حذف تکراری‌ها از کپی) اول در یک CSV نوشته می‌شوند که کاربر در Excel می‌بیند و اصلاح می‌کند؛ `apply` فقط همان CSV را اجرا می‌کند.
4. **وضعیت روی خود هارد ذخیره می‌شود** (پوشهٔ workspace)، با مسیرهای **نسبی**؛ پس با عوض‌شدن سیستم‌عامل، حرف درایو (`E:` ← `F:`) یا نقطهٔ اتصال (`/run/media/...`) چیزی خراب نمی‌شود.
5. **کار سنگین بدون هوش مصنوعی است.** پیمایش، hash، کپی و تطبیق کار کد است. هوش مصنوعی فقط برای پیشنهاد دسته‌بندی، فقط روی نام و مسیر (نه محتوا)، به‌صورت دسته‌ای و با برآورد هزینه پیش از اجرا استفاده می‌شود؛ و همیشه اختیاری است.
6. **قالب‌های باز.** SQLite، CSV (UTF-8 با BOM برای Excel)، Markdown و JSON؛ تا اگر versline در دسترس نبود، کار با `sqlite3`، Excel، پایتون یا هر ابزار دیگری ادامه پیدا کند.
7. **اثبات کامل‌بودن.** در پایان باید بشود نشان داد هر فایل منبع یا کپی شده، یا نسخهٔ یکسانش کپی شده، یا آگاهانه کنار گذاشته شده است.

| 4 | `export` | ✅ پیاده‌شده | کاتالوگ | `reports/files.csv` (همهٔ فایل‌ها با نوع و hash) | خیر |

## ۴. پوشهٔ workspace

پیش‌فرض: `_versline_organize` در **ریشهٔ درایو اولین منبع** (یا هر جا که با `-w` بدهید).

```
_versline_organize/
├── README.md              ← برنامه و وضعیت این پروژهٔ مشخص (برای انسان و دستیار هوش مصنوعی)
├── LOG.md                 ← دفتر کار: چه کسی، کی، چه کاری کرد
├── catalog.sqlite         ← منبع حقیقت: فهرست فایل‌ها، hash ها، تصمیم‌ها
├── taxonomy.txt           ← (مرحلهٔ ۶) دسته‌های مقصد
├── reports/               ← خروجی‌های قابل‌خواندن (Markdown/CSV)
├── plan/                  ← (مراحل ۷-۸) classify.csv، plan.csv
└── logs/                  ← لاگ اجراها
```

کاتالوگ مسیر ریشهٔ هر منبع را **نسبت به پوشهٔ والد workspace** (یعنی ریشهٔ درایو) ذخیره می‌کند. اگر منبع خارج از آن باشد، مسیر مطلق ذخیره می‌شود و به‌جای آن هشدار داده می‌شود.

## ۵. مدل داده (SQLite)

```sql
meta(key TEXT PRIMARY KEY, value TEXT)                 -- schema_version, created_at, ...
roots(id INTEGER PRIMARY KEY, label TEXT UNIQUE, path TEXT, is_relative INTEGER,
      last_scan_started TEXT, last_scan_finished TEXT)
files(id INTEGER PRIMARY KEY,
      root_id INTEGER, relpath TEXT,          -- مسیر نسبی با جداکنندهٔ "/"
      name TEXT, norm_name TEXT, ext TEXT,    -- norm_name: نام یکسان‌سازی‌شده (ی/ک، NFC، حروف کوچک)
      size INTEGER, mtime REAL,
      kind TEXT,                              -- book|document|audio|video|image|archive|software|font|web|junk|other
      partial_hash TEXT, full_hash TEXT,      -- sha256
      hash_size INTEGER, hash_mtime REAL,     -- اندازه/زمانی که hash برای آن حساب شد
      present INTEGER DEFAULT 1,              -- در آخرین scan دیده شد؟
      last_seen TEXT,
      UNIQUE(root_id, relpath))
dirs(id INTEGER PRIMARY KEY, root_id INTEGER, relpath TEXT,   -- relpath "" = خود ریشه
     file_count INTEGER, direct_size INTEGER,  -- فقط فایل‌های مستقیم
     total_files INTEGER, total_size INTEGER,  -- با همهٔ زیرپوشه‌ها
     image_count INTEGER, exe_count INTEGER,
     dominant_kind TEXT, dir_kind TEXT,       -- dir_kind: scan_folder|software|NULL
     UNIQUE(root_id, relpath))
scan_errors(id INTEGER PRIMARY KEY, root_id INTEGER, relpath TEXT,
            stage TEXT,                       -- scan|hash-partial|hash-full
            error TEXT, at TEXT)              -- برای هر (فایل، مرحله) فقط آخرین خطا؛ هر اجرا دوباره تلاش و به‌روز می‌کند
applied(key TEXT PRIMARY KEY,                 -- '<برچسب منبع>/<relpath>'
        action TEXT,                          -- copy|move
        dest TEXT, size INTEGER, sha256 TEXT,
        status TEXT,                          -- moving (قصد ثبت شده) | done | error | reverted
        error TEXT, at TEXT)
```

SQLite با `journal_mode=TRUNCATE` باز می‌شود: فایل journal بعد از هر commit خالی می‌شود، نه حذف. حالت پیش‌فرض (`DELETE`) روی محیط‌هایی که حذف فایل در آن‌ها ممنوع است (مثل پل دسترسی Claude به کامپیوتر کاربر) با `disk I/O error` شکست می‌خورد و WAL روی FUSE/درایو شبکه قابل‌اعتماد نیست.

نسخهٔ طرح در `meta.schema_version` ثبت می‌شود؛ تغییر طرح باید با migration انجام شود، نه ساخت دوبارهٔ کاتالوگ.

## ۶. الگوریتم‌ها

### ۶.۱ scan (پیمایش افزایشی)

- پیمایش با `os.scandir` (سریع، بدون `stat` اضافه روی ویندوز). پیوندهای نمادین دنبال نمی‌شوند.
- پوشه‌های سیستمی رد می‌شوند: `$RECYCLE.BIN`، `System Volume Information`، `.Trash-*`، خود workspace.
- برای هر فایل: اگر `(size, mtime)` با رکورد قبلی یکی باشد (با تحمل ۲ ثانیه برای تفاوت دقت زمان NTFS/FAT/FUSE)، hash های قبلی حفظ می‌شوند؛ وگرنه hash ها پاک می‌شوند تا دوباره حساب شوند.
- فایل‌هایی که در این scan دیده نشدند `present=0` می‌شوند (حذف نمی‌شوند).
- `last_seen` یک «توکن اجرا» است (زمان + شناسهٔ تصادفی)، تا دو scan که در یک ثانیه شروع شوند با هم قاطی نشوند.
- هر ۲۰۰۰ فایل یک commit؛ قطع‌شدن فقط همان دسته را از دست می‌دهد.
- خطاها (دسترسی، مسیر خیلی بلند، نام غیر UTF-8) در `scan_errors` ثبت می‌شوند و کار ادامه می‌یابد.
- در پایان، جدول `dirs` از روی `files` بازسازی می‌شود (تعداد، حجم، نوع غالب، تشخیص پوشهٔ اسکن/نرم‌افزار).

### ۶.۲ نوع فایل (kind)

بر اساس پسوند (جدول در `services/organize/kinds.py`) به‌علاوهٔ چند قاعدهٔ نام: `Thumbs.db`، `desktop.ini`، فایل‌های `~$...` (قفل Office)، `.tmp` ← `junk`.

### ۶.۳ پوشه‌های یکپارچه (واحد دسته‌بندی)

برخی پوشه‌ها را نباید از هم پاشید و باید **کل پوشه** یک واحد باشد:

- **پوشهٔ اسکن کتاب** (`scan_folder`): حداقل ۱۰ تصویر مستقیم و دست‌کم ۸۰٪ فایل‌های مستقیمش تصویر باشد.
- **پوشهٔ نرم‌افزار** (`software`): حداقل ۵ فایل `exe/dll/…` و دست‌کم ۳۰٪ فایل‌های مستقیمش از این نوع.
- (برنامه‌ریزی‌شده) **مجموعهٔ درس/جلسات**: پوشه‌ای که بیشترش صوت/ویدیو با نام‌های شماره‌دار است (`جلسه 1`، `جلسه 2` …).
- (برنامه‌ریزی‌شده) **صفحهٔ وب ذخیره‌شده**: `x.htm` + پوشهٔ `x_files`.

### ۶.۴ تشخیص تکراری (dupes)

سه مرحله تا کمترین مقدار خواندن از دیسک لازم شود:

1. گروه‌بندی بر اساس **اندازه** (فایل‌های صفربایتی و کوچک‌تر از `--min-size`، پیش‌فرض ۱ بایت، کنار می‌روند). فایل با اندازهٔ یکتا قطعاً تکراری ندارد.
2. **hash جزئی**: sha256 روی ۶۴KB اول + ۶۴KB آخر + اندازه. فقط برای گروه‌های هم‌اندازه.
3. **hash کامل** sha256، فقط برای گروه‌هایی که hash جزئی‌شان یکی است. هر hash بلافاصله ذخیره می‌شود، پس قطع‌شدن کار را از دست نمی‌دهد.

فایل‌های ≤۱۲۸KB در مرحلهٔ ۲ کامل خوانده می‌شوند و hash جزئی‌شان همان hash کامل است. هر ۱۵ ثانیه commit می‌شود و با Ctrl+C (یا SIGINT) هم پیش از خروج commit می‌شود. فایلی که خوانده نشد hash نمی‌گیرد و در اجرای بعد دوباره امتحان می‌شود.

**تجربهٔ اجرای واقعی (۱۴۰۵/۰۸/۱۸):** ۵۶٬۷۴۰ فایل، ۴۰۶ گیگ؛ scan حدود ۲۰ ثانیه؛ ۱۶٬۷۷۲ فایل هم‌اندازه (۵۰ گیگ) کاندید؛ hash جزئی و کامل حدود ۱۵ دقیقه از طریق پل FUSE (روی سیستم بومی سریع‌تر).

sha256 عمداً انتخاب شده تا با ابزارهای استاندارد قابل‌بررسی باشد: `sha256sum` (لینوکس) و `Get-FileHash` (PowerShell).

### ۶.۵ پوشه‌های زائد (redundant folders)

برای هر پوشه (در همهٔ سطوح): `redundant_bytes` = حجم فایل‌هایی از این پوشه که **نسخهٔ یکسانی بیرون از این پوشه** دارند. اگر نسبت آن به کل حجم پوشه ≥ ۹۰٪ و حجم پوشه ≥ ۱MB باشد، پوشه «تقریباً کامل جای دیگری هم هست». فقط بالاترین پوشهٔ واجد شرایط گزارش می‌شود (زیرپوشه‌هایش تکرار نمی‌شوند)، به‌همراه پرتکرارترین محل نسخه‌های دیگر. این گزارش برای تصمیم‌های درشت است («کل پوشهٔ X کپی Y است»).

### ۶.۶ یکسان‌سازی نام (normalize)

- فقط تبدیل‌های بی‌خطر: `ي`←`ی`، `ك`←`ک`، `ى`←`ی`، NFC، فاصله‌های تکراری. در `norm_name` (فقط برای مقایسه) علاوه بر این اعراب و تطویل (`ـ`) حذف و حروف لاتین کوچک می‌شوند. تبدیل‌های معنادار مثل `ۀ`←`ه` انجام نمی‌شود.
- نام **روی دیسک تغییر نمی‌کند**؛ `norm_name` فقط برای جست‌وجو و مقایسه است. در `apply`، نام مقصد با تابع `windows_safe_name` ایمن می‌شود (همان یکسان‌سازی ي/ك + حذف `<>:"/\|?*` و نویسه‌های کنترلی، حذف نقطه/فاصلهٔ انتهایی، پرهیز از نام‌های رزروشدهٔ `CON`، `PRN`، `AUX`، `NUL`، `COM1-9`، `LPT1-9`، حداکثر ۱۵۰ نویسه با حفظ پسوند).

### ۶.۷ دسته‌بندی با قاعده (`rules.txt`) و هوش مصنوعی (برنامه‌ریزی‌شده)

**قالب `rules.txt`** (در workspace؛ `#` توضیح است):

```
@dest_root      مرتب                       # پوشهٔ مقصد نسبت به ریشهٔ درایو
@default        ۹-بایگانی خام               # بی‌قاعده‌ها ← <default>/<برچسب منبع>/<مسیر>
@root_priority  منبع۱ | منبع۲               # برای انتخاب نسخهٔ نگه‌داشتنی و نام بدون (2)
@media_kinds    audio video                # این انواع move می‌شوند، بقیه copy
@media_folder_ratio 0.8                    # پوشه‌ای که ≥۸۰٪ حجمش صوت/ویدیو است، فایل‌های دیگرش هم همراه رسانه می‌روند
@media  ۱-کتابخانه => ۲-صوت و تصویر          # مقصد رسانه‌ها: پیشوند مقصد عوض می‌شود (طولانی‌ترین برنده)
منبع/پوشه یا فایل => مقصد/پوشه               # طولانی‌ترین پیشوند منطبق برنده؛ بقیهٔ مسیر حفظ می‌شود
```

- انطباق به ي/ك و فاصلهٔ اضافه حساس نیست. قاعده‌ای که به یک فایل اشاره کند، فایل را مستقیم در پوشهٔ مقصد می‌گذارد.
- **`assignments.csv`** (اختیاری، در workspace): تصمیم فایل‌به‌فایل با ستون‌های `root, path, dest, by, note`؛ `dest` پوشهٔ مقصد است و نام فایل حفظ می‌شود. بر هر قاعده‌ای مقدم است (`rule` در plan: `assign:<by>`) و پوشهٔ مقصدش دقیقاً رعایت می‌شود (قاعدهٔ «همراه رسانه» روی آن اعمال نمی‌شود). برای پوشه‌های دانلود که یکدست نیستند، به‌جای هزاران خط در `rules.txt` از این فایل استفاده می‌شود؛ سازندهٔ آن می‌تواند انسان، یک اسکریپت یا (در آینده) `classify --llm` باشد.
- `taxonomy.txt`: یک پوشهٔ مقصد در هر خط (`مسیر | توضیح`). `plan` مقصدهای بیرون از آن را (دو سطح اول) هشدار می‌دهد.
- زیرپوشه‌های منبع زیر مقصد حفظ می‌شوند، پس «تقسیم‌بندی‌های رده‌پایین‌تر» خودکار منتقل می‌شوند و فقط سطح ۱ و ۲ تعریف می‌شود.

**هوش مصنوعی** (اختیاری، `classify --llm`، هنوز پیاده نشده) فقط برای واحدهایی که قاعده‌ای نداشتند: ارسال دسته‌ای (۱۵۰ تا ۳۰۰ مسیر در هر درخواست) شامل مسیر نسبی، نوع و حجم، به‌همراه متن `taxonomy.txt`؛ پاسخ JSON با `category`، `confidence` و `reason`. پرامپت در `resources/prompts/organize_classify_prompt.md`. پیش از اجرا تعداد درخواست و برآورد توکن چاپ می‌شود (`--dry-run`). نتایج کش می‌شوند؛ اجرای دوباره فقط موارد باقی‌مانده را می‌فرستد.
3. خروجی به‌جای تصمیم مستقیم، **پیشنهاد خطوط `rules.txt`** است (پوشه‌ای ← دسته) تا همهٔ تصمیم‌ها در یک جا، قابل‌خواندن و قابل‌ویرایش بمانند. اطمینان کمتر از آستانه (پیش‌فرض ۰٫۶) پیشنهاد نمی‌شود.

### ۶.۸ plan / apply / verify / revert-moves

- **plan** (`services/organize/planner.py`): برای هر فایل حاضر در کاتالوگ:
  1. قاعده ← مقصد؛ بی‌قاعده ← `@default/<برچسب>/<مسیر>`.
  2. صوت/ویدیو: `@media` روی مقصد اعمال و اقدام `move`. فایل غیررسانه‌ای که پوشهٔ والدش ≥ `@media_folder_ratio` رسانه است: همان مقصد رسانه‌ای (یادداشت `with-media`) ولی `copy`.
  3. `junk` ← `skip_junk`.
  4. تکراری‌ها (فقط بین `copy` ها، بر اساس SHA-256): یک نسخه نگه داشته می‌شود؛ اولویت: مقصد غیر از بایگانی خام، `@root_priority`، مسیر کم‌عمق‌تر، کوتاه‌تر. بقیه `skip_duplicate` با `duplicate_of`. رسانه‌ها dedupe نمی‌شوند تا هر دوره کامل بماند.
  5. هر جزء مسیر مقصد با `windows_safe_name` ایمن می‌شود.
  6. برخورد نام (مقایسه بی‌حساس به حروف و ي/ك، مثل ویندوز): منبع با اولویت بالاتر نام اصلی را می‌گیرد، بقیه ` (2)` و یادداشت `renamed-collision`.
  7. هشدار مسیر بلندتر از ۲۴۰ نویسه و مقصد بیرون از taxonomy.
  خروجی: `plan/plan.csv` (ستون‌ها: `id, approved, action, root, path, dest, size, kind, rule, note, duplicate_of`) و `plan/plan_summary.md` (بر اساس اقدام، مقصد، قاعده؛ پوشه‌های بی‌قاعده؛ هشدارها). کاربر می‌تواند `approved` را `no` کند (Excel ← «CSV UTF-8»).
- **apply** (`applier.py`): فقط ردیف‌های تأییدشدهٔ `copy`/`move`؛ اول move ها (آنی)، بعد copy ها. `--dry-run`، `--only move|copy`، `--yes`، `--skip-unclassified` (ردیف‌های `rule=default` برای اجرای بعد می‌مانند؛ چون پس از apply تغییر مقصد یک فایل هنوز پشتیبانی نمی‌شود، بهتر است بی‌قاعده‌ها پیش از اجرایشان دسته‌بندی شوند). پیش از شروع: هم‌پوشان نبودن مقصد با منابع، فضای آزاد (+۲ گیگ). **copy**: نوشتن در `name.part` و hash هم‌زمان، تطبیق با `full_hash` کاتالوگ (اگر بود)، حفظ mtime، تغییر نام به نام نهایی. **move**: ثبت `moving` و commit، سپس `os.rename` (فقط اگر هم‌درایو)، سپس `done`. در پایان هر اجرا `logs/moves.csv` از روی جدول `applied` بازنویسی می‌شود (ستون‌های `at, status, from, to`، مسیرها نسبت به ریشهٔ درایو)، پس قطع‌شدن وسط کار آن را ناقص نمی‌کند. مقصد موجود: اگر همان محتوا بود «انجام‌شده» حساب می‌شود، وگرنه خطای conflict؛ **هیچ‌وقت بازنویسی نمی‌شود**. قابل‌ادامه: ردیف‌های `done` رد می‌شوند و `moving` نیمه‌کاره بررسی و تکمیل می‌شود.
- **verify**: برای هر ردیف plan یکی از `copied`، `moved`، `duplicate_ok`، `skipped_junk`، `excluded_by_user`، یا مشکل‌ها: `pending`، `error`، `MISSING_AT_DESTINATION`، `SIZE_MISMATCH`، `HASH_MISMATCH` (با `--deep`)، `moved_but_source_still_exists`، `duplicate_keeper_missing`. خروجی `reports/verify.md` و `reports/coverage.csv`.
- **پوشه‌های فقط‌خواندنی:** روی لینوکس، پوشه‌ای که ویندوز به آن ویژگی read-only داده (معمولاً پوشه‌های دارای `desktop.ini` و آیکون سفارشی) اجازهٔ جابه‌جایی فایل از آن را نمی‌دهد (`PermissionError`). این ردیف‌ها `error` می‌مانند و در اجرای بعدی روی ویندوز (که این ویژگی را برای پوشه‌ها نادیده می‌گیرد) انجام می‌شوند.
- **revert-moves**: همهٔ move های `done` را (جدیدترین اول) به جای قبلی برمی‌گرداند؛ کپی‌ها دست نمی‌خورند. بدون versline هم با `logs/moves.csv` (ستون‌های `from`، `to`) ممکن است.

## ۷. سازگاری ویندوز و لینوکس

| موضوع | راه‌حل |
|---|---|
| حرف درایو / نقطهٔ اتصال متفاوت | مسیرهای نسبی نسبت به ریشهٔ درایو در کاتالوگ |
| جداکنندهٔ مسیر | در کاتالوگ همیشه `/`؛ هنگام باز کردن به `Path` تبدیل می‌شود |
| مسیرهای بالای ۲۶۰ نویسه | پیشوند `\\?\` در ویندوز برای همهٔ عملیات فایل (`fs_path`) |
| دقت زمان تغییر | تحمل ۲ ثانیه در مقایسهٔ mtime |
| نام‌های نامعتبر در ویندوز | `windows_safe_name` در مقصد |
| کنسول ویندوز و فارسی | `cli.py` خروجی را UTF-8 می‌کند؛ گزارش‌ها فایل‌اند، نه فقط خروجی ترمینال |
| CSV فارسی در Excel | UTF-8 با BOM (`utf-8-sig`) |
| hard link | فقط NTFS/ext4؛ exFAT/FAT32 پشتیبانی نمی‌کنند → خطای واضح و بازگشت به copy |

**تجربهٔ اجرای `plan` (۱۴۰۵/۰۸/۱۸):** ۹۶ قاعده؛ ۴۶٬۱۶۲ copy (۱۰۰ گیگ)، ۴٬۹۰۳ move (۳۰۲ گیگ)، ۴٬۹۳۳ تکراری (۳٫۶ گیگ)، ۷۴۲ زائد؛ ۳۵۷ برخورد نام که همه هم‌اندازه بودند (احتمالاً نسخهٔ دوباره‌ذخیره‌شدهٔ همان PDF). ساخت plan چند ثانیه.

## ۸. هزینهٔ هوش مصنوعی

مثال: ۱۵٬۰۰۰ واحد بی‌قاعده، ۲۰۰ مسیر در هر درخواست ← ۷۵ درخواست؛ هر درخواست حدود ۸٬۰۰۰ توکن ورودی و ۶٬۰۰۰ توکن خروجی. با یک مدل ارزان (مثلاً Gemini Flash یا مدل‌های کوچک از طریق AvalAI/OpenRouter) هزینهٔ کل معمولاً در حد چند دلار یا کمتر است. عدد دقیق را `classify --dry-run` با ماژول `pricing` موجود برآورد می‌کند. اجرای بدون `--llm` هزینهٔ صفر دارد.
